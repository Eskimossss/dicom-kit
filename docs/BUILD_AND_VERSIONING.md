# Инструкция: Версионирование и сборка тестовых APK DICOM Kit

Данный документ описывает правила версионирования, внедрённые метаданные сборки и регламент создания проверочных тестовых APK в проекте DICOM Kit.

---

## 1. Схема версионирования

В проекте используется семантическое версионирование (`MAJOR.MINOR.PATCH[-PRERELEASE]`) в сочетании с монотонно возрастающим целочисленным `versionCode`:

- **Текущая тестовая версия Worklist:**
  - `versionName = "1.5.0-alpha.3"`
  - `versionCode = 10503` (после `10502` в `1.5.0-alpha.2`; схема монотонного инкремента сохранена).
- **Идентификатор приложения:** `ru.medeng.dicomtool` (не изменяется).
- **Подпись приложения:** сохраняется существующая конфигурация release-подписи из `keystore.properties` / переменных окружения.

### 1.1. Регламент изменения версий
- `1.5.0-alpha.1`, `1.5.0-alpha.2`, `1.5.0-alpha.3`... — промежуточные сборки этапа разработки Worklist.
- `1.5.0-beta.1`, `1.5.0-beta.2`... — сборки этапа комплексного ручного тестирования перед релизом.
- `1.5.0` — стабильный официальный релиз после согласования и одобрения.

**Важно:** `versionCode` **не** увеличивается при каждом локальном запуске Gradle. Он инкрементируется разработчиком только при подготовке новой проверяемой сборки (например, `10502` -> `10503` для `alpha.3`).

## 2. Метаданные сборки и экран «О приложении»

В `app/build.gradle.kts` настроена автоматическая генерация полей `BuildConfig`:
- `BuildConfig.VERSION_NAME` — строковое имя версии (например, `"1.5.0-alpha.1"`);
- `BuildConfig.VERSION_CODE` — целочисленный код (например, `10501`);
- `BuildConfig.BUILD_TYPE` — тип сборки (`"debug"` или `"release"`);
- `BuildConfig.GIT_BRANCH` — имя активной ветки Git (например, `"feature/stage-7-worklist-mwl"`), либо `"unknown"`, если Git недоступен;
- `BuildConfig.GIT_COMMIT_SHA` — короткий хеш коммита (например, `"d205a1d"`), дополняемый суффиксом `"-dirty"` при наличии незакоммиченных изменений в рабочем дереве;
- `BuildConfig.BUILD_TIME` — дата и время сборки в UTC (например, `"2026-10-20 18:10:00 UTC"`);
- `BuildConfig.IS_GIT_DIRTY` — логический флаг чистоты рабочего дерева.

### 2.1. Доступ через интерфейс
1. В приложении перейдите в **Действия и настройки** (иконка шестерёнки в верхней панели).
2. Нажмите на строку **О приложении DICOM Kit**.
3. Откроется экран **О приложении**, отображающий параметры сборки, описание приложения и ссылку на разработчика.
4. По нажатию кнопки **«Копировать информацию о сборке»** все параметры сборки копируются в буфер обмена устройства для передачи в отчётах об ошибках или журналах тестирования.

## 3. Debug и подписанный Release

Команды выполняются из `E:\Dicomtool` в Windows PowerShell 5.1 или PowerShell 7:

```powershell
.\build-test-apk.ps1                       # прежняя команда: Debug
.\build-test-apk.ps1 -BuildType Debug
.\build-test-apk.ps1 -BuildType Release
.\build-test-apk.ps1 -BuildType Both
.\build-test-apk.ps1 -BuildType Both -ReferenceReleaseApk .\builds\signing-reference\Dicom-Kit-v1.3.1.apk
```

SDK определяется через `ANDROID_SDK_ROOT`, `ANDROID_HOME` или `sdk.dir` в локальном `local.properties`. Используются `aapt` и `apksigner` именно из указанной в Gradle версии Build Tools (сейчас 36.0.0). Нужны Git, Gradle Wrapper и JDK 17+; при пустом JAVA_HOME используется существующий `C:\Program Files\Android\openjdk\jdk-21.0.8`.

Официальная проверяемая сборка требует чистого дерева, включая неигнорируемые untracked-файлы. `-AllowDirty` предназначен только для локальной диагностики: APK и JSON содержат dirty-маркер. Ошибки Git запрещают продолжение. Скрипт работает относительно собственного каталога, независимо от текущего каталога вызова.

Для Both сначала проверяются обе конфигурации подписи, затем `:app:assembleDebug :app:assembleRelease` выполняются одним вызовом Gradle. До и после сборки и сохранения сверяются HEAD, ветка, status и SHA-256 исходных файлов. Конфигурационный кеш отключён, чтобы Git-метаданные вычислялись заново. Изменение исходников/HEAD во время сборки приводит к ошибке.

В каждый APK добавляется `assets/dicom-kit-build.json`: полный HEAD, короткий коммит с dirty-маркером, ветка, версия, тип, UTC-время и публичный отпечаток сертификата. Значения генерируются из тех же переменных Gradle, что и BuildConfig экрана «О приложении». Проверяется JSON внутри готового APK, а не только файлы в каталоге сборки. Одинаковый SHA Git не означает побайтовой идентичности APK: время сборки и упаковка могут отличаться; идентичность файлов определяется SHA-256 самого APK.

### 3.1. Результаты и архивирование

- `E:\Dicomtool\builds\DICOM-Kit-1.5.0-alpha.3-debug.apk`
- `E:\Dicomtool\builds\DICOM-Kit-1.5.0-alpha.3-release.apk`

Рядом сохраняются `.apk.json` (версия, Git, подпись, размер, SHA-256, пути, время проверки) и `.apk.sha256`. Перед заменой APK предыдущий комплект копируется в уникальный подкаталог `builds/archive/<имя>-<UTC>-<GUID>/`; контрольная сумма архивной копии проверяется. Сохраняются даже побайтово одинаковые предыдущие экземпляры. Старые alpha.1 не изменяются. Старые APK без JSON сохраняются с имеющимися sidecar-файлами; неизвестные исторические Git-метаданные не выдумываются.

`-Force` оставлен для совместимости, но больше не разрешает потерю предыдущей сборки: архивирование обязательно. Новый APK сначала копируется во временный файл, проверяется по SHA-256 и переносится на основное имя. Ошибка записи/архивирования завершает скрипт с кодом 1. Файловая публикация двух APK не является транзакцией: при ошибке диска на втором файле первый может уже сохраниться; общий успех при этом не выводится. Все обязательные проверки обоих APK выполняются **до** начала сохранения.

### 3.2. Обязательная валидация

Проверяются существование и ненулевой размер, package name `ru.medeng.dicomtool`, versionName `1.5.0-alpha.3`, versionCode `10503`, debuggable-флаг, SHA-256, валидность подписи `apksigner verify --verbose --print-certs`, единственный подписант и совпадение его SHA-256 с сертификатом настроенного ключа. Затем сверяются встроенные Git-метаданные и тип APK. При любом несовпадении, неподписанном APK, ошибке Gradle/SDK или изменении исходников код возврата ненулевой. Both сообщает общий успех только после проверки и сохранения обоих вариантов.

## 4. Релизный ключ и совместимость

Существующий ключ хранится вне репозитория: `C:/Users/Eskimos/.android/keystores/dicomkit-release.jks`. Его пароли и alias читаются Gradle из игнорируемого `keystore.properties`:

```properties
RELEASE_STORE_FILE=<существующий путь; относительные пути считаются от app/>
RELEASE_STORE_PASSWORD=<локальный секрет>
RELEASE_KEY_ALIAS=<существующий alias>
RELEASE_KEY_PASSWORD=<локальный секрет>
```

Если соответствующее свойство отсутствует, используются `KEYSTORE_PATH`, `KEYSTORE_PASSWORD`, `KEY_ALIAS`, `KEY_PASSWORD`. Секреты не передаются аргументами команд и не попадают в APK/JSON. Keystore и конфигурация не должны добавляться в Git; `.gitignore` уже исключает `*.jks`, `*.keystore`, `keystore.properties`, `signing.properties`. На момент аудита таких файлов нет среди отслеживаемых файлов и в истории по указанным именам.

Открытый отпечаток **SHA-256 сертификата** существующего release-ключа:

```text
4690b671b00bdda65c9740a27dbd2250dc8ccbdd95797e112c3c4763aa6c1a8d
```

Он подтверждён `apksigner` на локальном подписанном `Dicom-Kit-v1.3.1.apk` (эталонная копия сохранена в `builds/signing-reference/`; package `ru.medeng.dicomtool`, версия 1.3.1 / 10301, SHA-256 файла `6558AF3429AF7349BA700C3B6CB34C84B4FB82383E455B433E471D12F05560B4`). Совместимость сертификатов с этим APK подтверждена; происхождение из публичной публикации отдельно не проверялось. Этот отпечаток закреплён в Gradle; debug-сертификат вместо него не принимается. Debug также не должен подписываться закреплённым release-ключом. Дополнительный `-ReferenceReleaseApk` проверяет подпись указанного эталона и совпадение сертификата перед сборкой.

Неполная конфигурация, отсутствующий keystore, неверный пароль/alias или другой сертификат останавливают подготовку Release. Даже прямой `assembleRelease` зависит от проверки ключа. Скрипт не создаёт и не заменяет релизные ключи, не использует debug-ключ для Release. При несовпадении требуется решение владельца ключа о восстановлении прежней конфигурации или отдельном согласованном плане смены подписи. Для Debug сохранено стандартное поведение Android Gradle Plugin: при первой сборке допускается создание обычного debug-keystore; проверка метаданных выполняется после `validateSigningDebug`.

Ручная проверка (предварительно настройте JAVA_HOME):

```powershell
& "$env:LOCALAPPDATA\Android\Sdk\build-tools\36.0.0\apksigner.bat" verify --verbose --print-certs .\builds\DICOM-Kit-1.5.0-alpha.3-release.apk
& "$env:LOCALAPPDATA\Android\Sdk\build-tools\36.0.0\aapt.exe" dump badging .\builds\DICOM-Kit-1.5.0-alpha.3-release.apk
Get-FileHash .\builds\DICOM-Kit-1.5.0-alpha.3-release.apk -Algorithm SHA256
```

## 5. Установка и обновление без удаления

Для обновления должны совпасть package name и совместимый сертификат подписи; versionCode должен быть не ниже установленного (повторная установка 10503 допустима при той же подписи). Существующие миграции и формат хранения также должны быть совместимы. Эта доработка не меняет миграции, DICOM, Worklist, UI или данные; практическая совместимость хранения на физическом устройстве требует ручной проверки с резервной копией.

Перед установкой проверьте установленный пакет, его versionCode и сертификат, сохраните резервную копию настроек/данных штатными средствами. Затем:

```powershell
adb -s <serial> install -r .\builds\DICOM-Kit-1.5.0-alpha.3-release.apk
adb -s <serial> shell am start -n ru.medeng.dicomtool/.MainActivity
```

Откройте «О приложении» и сравните тип release, версию, ветку, коммит с `.apk.json`; проверьте сохранность настроек и Worklist на синтетических данных. Debug и Release имеют одинаковый applicationId, но разные сертификаты и поэтому не обновляют друг друга. При ошибке подписи остановитесь; не удаляйте приложение и не очищайте данные ради установки. Скрипт сборки не выполняет adb-команд, uninstall, очистку или миграции.

При аудите 20.10.2026 на эмуляторе была установлена Debug alpha.2 (10502), поэтому замена её на Release без удаления была невозможна. Для alpha.3 Android/UI-тесты выполняются в отдельном пакете `.storagesafetytest`; обычная установка и её данные не затрагиваются. Установка и запуск Release на физическом устройстве не проверены.

## 6. Оптимизация и проверки

Release: `isMinifyEnabled = false`, `isShrinkResources = false` (явно). В `proguard-rules.pro` уже есть keep/dontwarn для `org.dcm4che3.**`; при выключенной минификации эти правила не выполняют shrink. Они не доказывают безопасность будущей минификации. Для её включения отдельно нужны регрессии DICOM VR/Sequence, чтения словарей, сериализации, отражения и сетевых SCP/SCU/MWL-сценариев. Настройки оптимизации библиотек в этой работе не менялись.

```powershell
.\tests\Test-ApkBuild.ps1
.\tests\Test-ApkSigning.ps1  # после сборки обоих APK; реальные Gradle/SDK, без изменения ключей
.\gradlew.bat testDebugUnitTest
.\gradlew.bat lintDebug
.\build-test-apk.ps1 -BuildType Debug
.\build-test-apk.ps1 -BuildType Release
.\build-test-apk.ps1 -BuildType Both
```

Регрессии PowerShell не требуют Pester. Они проверяют метаданные, тип, подписантов, отсутствие/пустой APK, архивы и sidecar-файлы при быстрых повторениях, повреждённую копию, ошибку Gradle, изменение исходников (в том числе при неизменном dirty-status) и отказ Git. Интеграционный набор использует изолированную копию конфигурации без релизных секретов в игнорируемом `builds/signing-tests-*/`: проверяет отсутствие ключа в Release/Both, отклонение настоящего debug-ключа, первую сборку Debug с отдельным временным Android user home, настоящий неподписанный APK, неверные versionCode/Git и другой сертификат. Никаких медицинских данных в тестах нет.

Результаты аудита и диагностики 20.10.2026: 28 регрессионных тестов скрипта и 8 интеграционных проверок подписи/SDK — PASS; unit-тесты — 288, ошибок/падений 0, пропущен 1; lintDebug — 0 ошибок, 44 предупреждения; диагностический Both под Windows PowerShell 5.1 прошёл aapt/apksigner. Финальные проверяемые APK формируются после коммита из чистого Git без `-AllowDirty`; точные Git SHA, размеры и контрольные суммы находятся в соседних `.apk.json`, результаты команд — в локальных `builds/*log`. Предыдущие исправления MWL: [STAGE_7_AUDIT_FIXES.md](STAGE_7_AUDIT_FIXES.md).
